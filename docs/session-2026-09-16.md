# Session log, 2026-09-16

The work behind the image, in the order it happened, wrong turns included.

The goal was one thing: a deck panel on the host screen has a grid of actions,
and the macropad should show the same colours on the same keys, so a key can be
found by matching it to the screen instead of counting positions.

## Starting point

The macropad ships with Framework's QMK firmware, and VIA can talk to it. What
VIA cannot do on that firmware is set per-key colour. The keyboard-specific
custom channel (`via_custom_value_command_kb`, channel 0) is not implemented, and
QMK's own RGB matrix channel holds one colour for the whole matrix. Framework's
`qmk_hid` has the same ceiling: brightness, effect, effect speed, hue,
saturation, all global.

So the colour had to come from firmware.

## Build

I used Framework's QMK fork, branch `fl16-2025`, because the macropad's keyboard
definition is not in upstream QMK. The toolchain and the commands are in
[BUILD.md](BUILD.md); the only surprise was the Python 3.12 problem, which ate
more time than it should have because the makefile reports it as `Platform not
defined` instead of as the exception it is.

The first build was `-km default` with the new source file added. That flashed
and worked, in the sense that the module still typed. The palette was painted on
every layer, and the layer keys did not do what the keymap said. They were
separate bugs, and each one made the other look worse.

## First flash, and what it took

The module is an RP2040 with the RP2040 bootloader, so the route in is the
bootloader command over raw HID. Framework intercepts VIA's bootloader command id
(`0x0B`) in `keyboards/framework/factory.c` and reads the next byte as one of
their own factory commands. The jump is therefore:

    [0x0B, 0xFE]      over the VIA raw HID interface

Plain `[0x0B]` does nothing. Their code logs `Unknown factory command: 0` and
returns before QMK sees it. `QK_BOOT` written into the EEPROM keymap did nothing
either, tried twice on layers 1 to 3, so that route is not worth retrying on this
firmware.

The bootloader's volume is not necessarily the raw disk. On this host it
appeared as a partition of a new disk rather than the disk itself, and mounting
the whole-disk node failed. Matching on the `RPI-RP2` label is the portable way
to find it and is what the flasher does.

The first flash also reset the EEPROM keymap. 72 of 320 keycodes changed: the
module came back running Framework's compiled default layout, not the user's
remap. The dump was restored over VIA from a 640-byte hex file, 23 chunks of
`set_buffer`, and verified byte for byte afterwards. That is why the flasher now
takes a fresh dump before anything else and puts it back afterwards.

After the flash, the hidraw node came back as `root:root 0600` with no ACL, even
though udev's database showed the `uaccess` tag from the existing rule. Only root
could open it, so the host-side tool saw an unreadable module and the panel
stayed shut. `udevadm trigger --action=add --subsystem-match=hidraw` brought the
ACL back. The flasher now re-triggers udev and waits before it reports a failure
to open the module, and the rule grants the `input` group as well; that group is
what made the node readable here, and FLASHING.md writes down what it costs.

## The layer hook collision

Framework's macropad firmware has two layer hooks that name layers by number:
`led_update_user` in the default keymap, and `keyboard_post_init_user` in
`macropad.c`. `_FN` is layer 1 there, and the one that fires on every LED update
is `led_update_user`:

    if (led_state.num_lock) { layer_off(_FN); } else { layer_on(_FN); }

This module runs an EEPROM keymap whose layer 1 is the user's tc1, so every
numlock update reached in and cleared the layer the user had just selected.
`TO(1)` set `layer_state = 2` and the hook took it straight back to 0, which made
tc1 behave like tc0. The panel, which identifies the layer by its colour, saw no
change and kept the palette on.

The fix is `keymaps/palette/keymap.c`: Framework's keymap with the hooks that are
in it removed (`led_update_user` and `enable_factory_mode`). Their
`keyboard_post_init_user` lives in `macropad.c`, runs once at boot, and does no
harm, so it stays. The EEPROM keymap supplies the real layout; the compiled one
only has to not interfere with it. That is why the build uses `-km palette` and
not `-km default`.

## The layer mapping, measured

After the fix, the layer state was read over the diagnostic channel with the
panel's keymap. `layer_state` is a bitmask, so `TO(n)` shows up as `1 << n`; the
layer colour is set from the highest layer in force.

| key | `layer_state` | active layer | colour (hue, sat) | panel palette |
|---|---|---|---|---|
| tc0 | 1 | 0 | 128, 255 | on |
| tc1 | 2 | 1 | 85, 255 | off |
| tc2 | 4 | 2 | 42, 255 | off |
| tc3 | 8 | 3 | 0, 255 | off |

Before that table existed, "the panel did not change" could mean three things:
the keypad had not changed layer, the hook had already undone it, or the firmware
had not noticed either way. The diagnostics (`0xF0`, `0xF1`, described in
[PROTOCOL.md](PROTOCOL.md#diagnostics-0xf0-and-0xf1)) were added so the module
could answer the question itself instead of the host inferring it from a colour.

## The keymap the keypad runs

`keymap-dumps/eeprom-keymap-2026-09-16.hex` is the EEPROM keymap as it stood
during this work: the four layer keys `TO(0)` to `TO(3)` on layer 0 at matrix
positions (2,1), (2,2), (3,4) and (2,4), Framework's numpad layout around them,
and modifier combinations on the top row.

`keymap-dumps/framework-default.hex` is what a flash leaves behind: Framework's
compiled layout, with the RGB controls on layer 1 and their factory test alphabet
on layer 2. Layers 3 to 9 are transparent. Keep a copy of it, or Framework's
published stock image, as the way back.

Three dumps were committed under the names before-remap, after-remap and
their-original-layout, and all three were byte-identical. They were one snapshot
under three names; two were dropped.

## Palette design

The first version painted every key on every layer. That was wrong before anyone
had to explain why: the panel only owns layer 0. The four layer keys select
layers; the palette is only meaningful on layer 0. So `rgb_matrix_indicators_advanced_kb()` returns early when the active
layer is not 0 and leaves the configured effect to paint the matrix, exactly as
it did before this file existed.

The second wrong version painted the fifteen panel keys at full colour and left
the other nine keys dark. That looked like a keypad with dead keys. What works is
the nine at 30 percent brightness in the active layer's colour: dim enough to
read as "not a panel key" whatever the hue, bright enough to see which layer is
selected.

The default palette (what the keypad shows before the host pushes its own) needed
hues that do not look alike. The fifteen painted cells get hues evenly spaced by
17 around the 256-step wheel, then shuffled rather than laid out as a rainbow, so
keys that share an edge are at least 35 hue units apart; the diagonal pairs were
not constrained. The colours are written out as RGB rather than computed at
boot because every init hook this keyboard has is already taken: Framework's
shared `framework.c` defines `keyboard_post_init_kb`, and `macropad.c` has the
`_user` one.

The LED map came out of `g_led_config` in Framework's `macropad.c`, not out of a
drawing of the keypad. The driver map in that file is re-arranged into LED id
order precisely so it does not match the visual order; reading positions off a
photo would have quietly painted the wrong keys.

## What it costs on the host

The host-side tool that drives this is not in this repo, so these numbers are
context rather than something you can reproduce from here:

* the panel appears 0.09 s after a layer key, down from about 1.4 s while the
  panel waited for its poll;
* the process costs 9 to 13 percent of one core, split between the key watcher,
  the gate (the rule for when the panel should be on screen at all) and the
  content refresh;
* a full palette is 15 reports, 45 bytes of colour in total, and needs no
  reflash to change.

## Left open

* the panel title does not name the layer;
* the empty sixteenth cell of the panel grid is invisible against the panel's
  theme;
* deck-mode previews are rendered 1:1 while the macropad's are rendered 2x;
* tc2 and tc3 have not been pinned by name in the host tool.

## What I would do differently

Take the keymap dump before the first flash, not after. Next time I would write
the diagnostics before debugging the layer hooks, and pin the build tree so the
image can be rebuilt and compared instead of described.
